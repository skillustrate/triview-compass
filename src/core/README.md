# Core runtime

Provider-neutral v1 input, policy, capability, result, report, and audit schemas are defined in [contracts/schemas](../../contracts/schemas/). `preflight.js` accepts explicit UTF-8 text-file requests and a trusted policy, checks path, file, changed-line, and byte limits, excludes sensitive/generated paths, redacts documented credential, private-key, and Bearer-header token patterns, and returns a frozen-content hash and sanitized bundle. `git-capture.js` accepts full base/target commit IDs and a trusted absolute repository path, requires ancestry, reads committed Git objects without working-tree content, rejects symlinks/submodules, and reports binary files without their contents. Both paths use the same sanitizer. Detection is best effort, not a guarantee against secret disclosure. The optional scanner callback is for a trusted host adapter and adds spans to the built-in scanner; overlapping or invalid spans stop preflight.

The file and Git entry points validate raw requests and complete policies against the checked-in Draft 2020-12 schemas before capture. `model-preflight.js` checks provider allowlisting, local or hosted data handling, declared harness/model controls, model capacity, and conservative per-role token bounds. Policies may select one provider for all roles or an explicit `roleRoutes` entry for every selected reviewer. `adapter-handshake.js` obtains fresh runtime capability documents from each selected adapter and counts the exact serialized request for each reviewer before returning an immutable plan. It makes no model calls. The dispatcher rechecks the policy and effective controls before invocation. The core cannot independently prove adapter claims.

`prompt-builder.js` constructs role prompts with concise, fixed guidance for every required skill from the frozen sanitized bundle. It sends opaque file IDs and scope counts, keeping real paths in a local resolver. The full skill documents remain references, not model payloads. `prepare-review.js` binds the builder to the adapter handshake. A real adapter must count its exact serialized payload, and any budget override must be explicit. Source-free Bionic probes measured 1,150, 1,430, and 1,208 input tokens for code-quality, security, and performance prompts containing one tiny synthetic file. Larger changes still need conservative preflight counts.

`review-dispatch.js` uses the prepared requests to start every selected reviewer independently through its selected adapter's `invokeReview` method. The adapter receives one exact payload, its input-token upper bound, a fresh invocation ID, an empty tool list, disabled memory, an output limit, and an abort signal per role. Core checks result schemas, per-role invocation and adapter identity, prompt version, required skills, distinct context IDs, output size, known secret patterns, and file-ID/line anchors. Reports attribute each reviewer to its adapter and model. Exact duplicates are grouped; severity disagreements and unverified findings remain visible. Failed reviewers make the report incomplete. Partial reports name omitted roles. The adapter must actually enforce fresh provider sessions, tool restrictions, output limits, and cancellation; this core cannot prove those claims from returned IDs alone. A static review harness, Claude Code adapter, and LM Studio adapter exist outside the core. Broader model-quality evaluation and live repository source-review verification remain outstanding.

Both capture paths use the policy's `timeoutSeconds` as a preflight deadline and return deeply frozen sanitized bundles only after successful capture and scanning. Git subprocesses receive the remaining time and are killed on timeout. Built-in and trusted synchronous JavaScript scanners run with a VM execution timeout; failures and timeouts return sanitized errors and no bundle. The trusted scanner callback must return spans synchronously. The deadline bounds preflight work; reviewer timeouts and the bounded Podman execution timeout are enforced by their respective runtimes. `audit.js` builds a schema-checked metadata record from a completed or incomplete run and hashes a canonicalized policy; callers must supply reviewer and validation outcomes. It never copies source content, paths, prompts, or transcripts into that record.

`audit-store.js` provides opt-in metadata persistence. Callers supply a directory and retention period (0–3650 days); zero disables storage. Stored records are schema checked, written as mode `0600` JSON files, and old valid audit files are pruned by record timestamp. The store leaves unrelated and malformed files alone. The application calls it after reviewer and optional sandbox outcomes are validated.

Remaining work includes broader production adapter verification and model behavior evaluation. The core must not contain provider-specific API calls or silently grant tools to reviewer sessions.

`static-review.js` is the report-only application entry point. `runStaticReview({ request, policy, repositoryPath, scan, modelAdapter })` supports the legacy single-adapter policy. A routed policy instead supplies `modelAdapters` keyed by reviewer role. It validates input, captures supplied files or committed Git changes, creates the bound static harness, and runs independent reviewers through those adapters. The caller must explicitly select the matching provider and data handling for every role.

Optional `sandbox: { image, command }` requires policy execution opt-in. The workflow copies and freezes policy, executes only the captured sanitized non-deleted files in rootless Podman, adds a schema-checked `sandbox` result, and records status/profile/image identity in metadata-only audits. A failed or skipped requested check makes the report incomplete. `sandboxAdapter.runVerification` is a trusted, backend-neutral interface supplied by the host. The CLI supplies the Podman adapter; backend runtime options are not accepted from CLI JSON. Sandbox output is scanned and remains outside reviewer prompts.

`preflight-report.js` produces a frozen schema-checked capability report from the prepared request plan. `runStaticReview` accepts `onPreflight`, `preflightOnly`, and an optional trusted `harnessAdapter`; default static-harness behavior remains available. Preflight exposes routes, token bounds, control states, coverage counts, sandbox readiness, retention configuration, and adapter limitations without source or local account paths. Normal reports embed it. Refused preflight-only requests return a sanitized refusal; normal reviews retain typed errors. Audit configuration is validated before calls.
