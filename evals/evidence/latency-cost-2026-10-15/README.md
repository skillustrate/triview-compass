# Latency and cost, measured against three real local PRs (2026-10-15)

Phase 9's work item asks for end-to-end latency/cost across "a typical PR size," citing the Phase 7 multi-repo corpus as the source of real changes. The external repositories that corpus was built from (minimist, curl, kubernetes, etc.) were cloned locally for that work and are not available in this environment any more — re-cloning them was judged unnecessary for what this measurement actually needs, which is real code changes of varying size, not specifically *those* changes again. Instead, this measurement uses three real commits from this project's own history, spanning small/medium/large, reviewed live through the real, already-authenticated Claude Code CLI on this machine (`claude --version` → `2.1.300`, matching the pinned adapter version). This is a disclosed scope deviation from "the Phase 7 corpus" specifically, not a silent substitution.

## What was measured

| Size | Commit | Files changed (raw diff) | Included after path exclusions | Input token bound (per reviewer) | Wall-clock latency | Outcome |
| --- | --- | --- | --- | --- | --- | --- |
| Small | `ecf1ffa` (single-runtime adapter-config fix) | 3 | 2 | ~101–102k | **9.24s** | `complete`, `request-changes`, 1 finding |
| Medium | `d41cc11` (GitHub Actions template) | 8 | 6 | ~98.7–99.9k | **10.37s** | `complete`, `request-changes`, 6 findings |
| Large | `e78ea28` (setup wizard, ~500 lines) | 6 | 4 | ~127–128k | **14.75s** | `complete`, `request-changes`, 5 findings |

Each case excluded `STATE.md`/`plan.md` via `--policy-overrides`-style path exclusions — this project's own running handoff logs are appended to on every commit regardless of the code change's size, so including them would have measured "how big is today's narrative entry," not "how big is this PR." All three reviewers completed for all three cases; no refusals, no timeouts (the default 120s-per-reviewer budget was never close to exercised). Full reports are alongside this file (`report-small.json`, `report-medium.json`, `report-large.json`).

**Latency scales with included content, roughly as expected** (9.2s → 10.4s → 14.8s as included token bound rose from ~102k to ~128k), but the dominant fixed cost is Claude Code's 65,536-token protocol reserve (see "A budgeting finding" below) — even the smallest real change here needed a budget nearly double the project's own shipped default to clear preflight at all.

## Cost

**Not measurable through the Claude Code adapter.** Its `getCapabilities()` reports `usageReporting: 'unsupported'` — a flat subscription has no per-call token or dollar accounting exposed to this project's adapter, so there is no `tokenUsage` field to report here (consistent with the already-disclosed limitation in `docs/report-contract.md` and `RELEASE.md`). This is itself evidence for the backlog item recorded in plan.md's Phase 9 progress notes: a direct hosted-API model adapter (calling a provider's own metered HTTPS API) would expose real token counts and a real dollar estimate, where a subscription CLI fundamentally cannot. Anyone on a metered API plan instead of a flat subscription should expect real per-call cost proportional to the input token bounds in the table above, not zero.

## A budgeting finding, not just a number

The default budget in `examples/claude-code-policy.json` (`maxInputTokensPerReviewer: 100000`) was **insufficient for two of the three cases** — both the small and large cases refused preflight with `BUDGET_EXCEEDED` until raised to `200000`. This is not a quirk of these specific commits: it follows directly from `PROTOCOL_RESERVE_TOKENS = 65536` in `src/adapters/model/claude-code.js` (a fixed allowance for the CLI's own wrapper, not available for actual content) leaving only ~34k tokens of real headroom under the default budget — and this project's own commits routinely touch several whole files (full file content is sent, not just diff hunks; see `src/core/git-capture.js`), which adds up quickly even for a small change. The Phase 7 corpus's own case notes already recorded this pattern repeatedly (see `evals/corpus/README.md` and individual case files); this measurement reproduces it against fresh, real data rather than only citing the earlier finding. **Anyone adopting the shipped default policy for anything but a genuinely tiny change should expect to need `--policy-overrides` to raise `maxInputTokensPerReviewer`, not treat the default as generally sufficient.**

## The actual headline result: this surfaced real, unfixed bugs

Running these three live reviews against this project's own recent commits was itself a useful exercise, independent of the latency numbers: the code-quality and security reviewers found **12 real findings across the three cases**, several of them genuine, previously-unnoticed defects in code shipped earlier in this same work session — the GitHub Actions template and the setup wizard. This is now the actual point of this measurement's write-up, not a footnote to it.

Confirmed and fixed as a direct result (see `STATE.md`/`plan.md`'s handoff entries and the commit this evidence ships alongside):

- **Required, security** — `setup.js` wrote `adapter-config.json`/`routes.json` (which may hold API keys/tokens a user typed in) with default file permissions, typically world-readable. Fixed: both files and their directory are now written with owner-only permissions (`0o600`/`0o700`).
- **Required, correctness** (shipped as a security-relevant fix) — `triview-review.yml` interpolated a GitHub Actions secret directly into a shell string via `${{ }}`, so a quote, backtick, or `$(` in the secret's value could corrupt the file or run arbitrary shell commands. Fixed: the secret now passes through `env:` and is written with `printf '%s'`.
- **Required, correctness** — `setup.js` never validated the audit-retention-days or audit-directory answers against the exact format `review.js` requires, so the wizard could print a command that `review.js` would reject. Fixed: both are now validated and re-asked on an invalid answer, before anything is written or printed.
- **Required, correctness** (confirms a bug already found and fixed earlier in this session, at an earlier revision) — the large case's target commit was the one *before* the single-runtime adapter-config fix (`ecf1ffa`), and the reviewer independently rediscovered the exact same bug this project's own live interactive run had already caught and fixed. Treated as corroborating evidence the tool works, not a new action item.
- **Optional, correctness** — the printed command joined arguments with a plain space, so a path or value containing a space (e.g. a working directory with a space in it) produced a command that couldn't be pasted and run correctly. Fixed: every argument is now single-quoted for display.
- **Optional, correctness** — `review.js`, `setup.js`, and `build-review-request.js` all used the same `new URL(\`file://${process.argv[1]}\`)` pattern to detect direct invocation, which doesn't percent-encode spaces/`#` and mishandles Windows paths. Fixed in all three to use `pathToFileURL`.
- **Optional, correctness** — `setup.js` didn't cross-check a "no, keep my code local" answer against a detected *hosted* assistant, so the wizard could write an internally inconsistent policy that would fail confusingly later. Fixed: this combination is now caught and rejected before anything is written, with a clear explanation.
- **Optional, supply-chain** — the workflow template pinned GitHub Actions to mutable version tags (`@v4`, `@v7`) while holding `pull-requests: write` and a model credential secret — a compromised tag would be a real exfiltration path. Fixed: pinned to the exact commit SHA each tag currently resolves to, verified live via `gh api` rather than guessed (`actions/checkout` → `v4.4.0`, `actions/setup-node` → `v4.4.0`, `actions/github-script` → `v7.1.0`).
- **Optional, security** — the posted PR comment embedded untrusted review output (derived from the reviewed PR's own diff) inside a fixed triple-backtick fence, so a crafted finding or diff line containing its own triple backticks could break out of the fence and render as live markdown. Fixed: the fence is now sized longer than the longest backtick run actually present in the body.

Documented as a disclosed, not-fully-solved risk rather than papered over (see `examples/github-actions/README.md`'s new section): the workflow reads `.triview/policy.json` from the pull request's own head checkout, so a malicious PR author can edit the policy controlling their own PR's review (budgets, exclusions, data handling) before the workflow reads it. Properly fixing this means checking the policy out from the base ref specifically, which is a real per-repository design decision this template cannot make unilaterally for every adopter.

This is the clearest demonstration this project has produced so far of its own stated value proposition — an advisory second opinion catching real, specific, actionable problems in freshly-written code, including code written by the same session that's now reviewing it.
