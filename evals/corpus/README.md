# Real-change evaluation corpus (Phase 7)

The commands here explicitly select the Claude Code reference adapter to reproduce its recorded evaluations. They do not set a default harness; see [harness selection](../../docs/harness-selection.md) for choosing another adapter. Historical reports retain their original runtime attribution.

Measuring accuracy on real changes is required, because the synthetic suite in `evals/behavior/` and the single two-file pilot in `evals/pilots/git-capture/` do not establish general accuracy. This directory is where that measurement lives: one manifest per real change, a recorded human disposition for every finding the pipeline produced, and an aggregate metrics log.

This is **not** a replacement for `evals/behavior/` (synthetic, deterministic oracles, no live model calls needed to validate structure) or `evals/pilots/` (the original single-case pilot, preserved as-is). It is the corpus-scale successor to those.

## Case manifest format

Each case is a directory under `cases/` containing:

- **`case.json`** — the manifest: `id` (must equal the directory name), `status` (`pending` / `run` / `dispositioned`), `source` (repository + base/target revisions), `groundTruth` (`type`, `description`, and what a correct reviewer should and shouldn't flag), `requestPath`/`policyPath` (relative to the case directory), and `runs[]` — one entry per time the case was actually executed, each with a `reportPath` and a `dispositions[]` array.
- **`request.json`** / **`policy.json`** — the exact CLI inputs (see `src/cli/README.md`). `policy.json`'s `pathPolicy.excludedPathGlobs` should be generated with `evals/scripts/scope-policy.js` against the target revision's tree, not hand-maintained — the original git-capture pilot's hand-written exclude list is what the 001 case migrated away from, specifically because a hand list silently under-excludes as a tree grows.
- Each disposition: `findingId`, `reviewer`, `severity`, `verdict` (`confirmed` / `rejected` / `unresolved`), and for a rejection a `reasonCode` (e.g. `wrong-anchor`, `incorrect-claim`, `not-change-relevant`) plus a `note` explaining why, following the disposition process in the main [README.md](../../README.md)'s "Before acting on a finding" checklist.

`npm test` (via `run-evals.js`) structurally validates every `case.json`: status enum, required fields, that `requestPath`/`policyPath` resolve to real JSON files, that a `dispositioned` case actually has at least one recorded disposition, and that every disposition verdict is a recognized value. It does not and cannot validate that a disposition's human judgment is correct — that's the point of having a human record it.

## Generating a new case's policy

```sh
node evals/scripts/scope-policy.js \
  --repository /path/to/repo \
  --revision <target-sha> \
  --include path/to/changed/file.js \
  --include path/to/changed/file.test.js \
  --out /tmp/scoped.json
```

This lists every tracked file at the target revision and excludes everything except the explicit `--include` list, so the policy can never accidentally include a file added after the exclude list was written. Before trusting it for a case, confirm with `git diff --name-status base..target` that no file the diff deletes is missing from the generated tree-based list (a deleted file won't appear in `git ls-tree` of the target revision, but it also can't leak content if it's absent from the target tree — still worth checking, as case `002`'s manifest notes).

Output globs collapse a whole excluded directory into one `dir/**` entry wherever nothing included lives under it, rather than one entry per file — case 011's repository has ~19,000 tracked files, and the original per-file generator produced a 1.7MB, 18,708-entry `policy.json` for it. That same per-file version also had a real bug: it escaped special glob characters (`*?[]{}`) with a backslash, but `src/core/preflight.js`'s glob compiler (`compileGlob`) refuses any glob containing `?{}[]` or a backslash outright, with no escape mechanism — so an escaped literal would have been rejected by the real system anyway. Neither bug happened to trigger on cases 001-009's actual trees (by luck of which filenames those repos happen to have), so it went unnoticed until a repo large enough to hit the size problem forced a closer look. The generator now throws a clear error naming the offending path instead of silently emitting an unusable glob, and all existing cases' policies were regenerated and reverified to produce identical included/excluded scope counts before case 011 was added.

## Running a pending case

```sh
node src/cli/review.js \
  --request evals/corpus/cases/<case-id>/request.json \
  --policy evals/corpus/cases/<case-id>/policy.json \
  --repository /path/to/repo \
  --harness claude-code --model sonnet --context-window 200000 --format json > /tmp/report.json
```

This requires a local Claude Code subscription per `src/cli/README.md` and sends sanitized source to that provider — review the request/policy's `dataPolicy` before running. After it completes:

1. Save the report under the case directory (e.g. `report.json`), add a `runs[]` entry pointing to it.
2. Disposition every finding per the main README's checklist: evidence, correctness, change relevance, severity, recommendation. Record `confirmed` / `rejected` / `unresolved` with a reason for each.
3. Set `status` to `dispositioned` once at least one disposition is recorded.
4. Run `npm run corpus:score` to append the updated aggregate metrics to `metrics-log.jsonl` and print a summary.

## Scoring the corpus

```sh
npm run corpus:score
```

Reads every `case.json`, computes (across all `dispositioned` cases): the confirmed-true-positive rate among `Critical`/`Required` findings, the wrong-anchor rate among all rejected findings (any severity — a wrong anchor on an `Optional` finding is still a wrong anchor), and how many `known-defect-present` cases had no confirmed finding in any run (a miss). It appends one line to `metrics-log.jsonl` and never overwrites a prior entry, so the trend over time stays inspectable. It makes no model or network calls — it only reads what's already on disk.

The script also warns to stderr when the corpus is below 20 cases or has pending cases, so a thin or incomplete corpus can't be mistaken for a finished measurement by only looking at stdout.

## Growing the corpus toward a representative target

To reach a credible 20–30-case corpus:

- **Diversify sources further.** Sixteen of twenty cases are now external, spanning seven ecosystems (Python/PyPI, JS/npm, Go, Rust/crates.io, Java/Maven, C#/.NET, C). minimist, the regex crate, and curl are each used three or more times, so ecosystem count overstates true diversity. The two gaps this section used to name — no case from a non-web/backend domain, and no true monorepo — are now closed: 015/018 (numpy) and 016/020 (curl) cover data-science and systems-programming domains respectively, and 017/019 (kubernetes, 19,298 tracked files at the reviewed revision) is a genuine monorepo, as opposed to case 011's jackson-databind, which was a large repository but not a multi-component one. For external cases, a public vulnerability database (`https://api.osv.dev`, GitHub Security Advisories, NVD) cross-referenced against `git log --reverse -S<fragment>` or `git log --follow` on the affected file — the recipe used for cases 003/004/009/010/011/013/019 — is a reliable, low-effort way to find a commit with already-published, independently-verified ground truth, rather than needing to personally assess an unfamiliar codebase's history from scratch. Case 020 instead used a commit-message `--grep` search (`git log --oneline -i --grep=<pattern>`) to find its routine, non-CVE target, since `known-clean` cases don't need a vulnerability database at all.
- **Add more `known-defect-present` cases.** Four exist now (003, 004, 009, 019), still too few to say anything about miss rate. Case 019 is the first where a reviewer's severity *calibration* (correctly scoring a real, non-security-severity defect as `Optional` rather than over-flagging it) is the interesting result, not just detection.
- **`known-clean` (routine, nothing-to-find) cases matter as much as defect cases.** Three exist now (007, 012, 020), still disproportionately few against thirteen `known-fix` cases. 007/012 are each a single whole non-code file (a README, a 73KB changelog) chosen partly because the file itself was unusually large — a reminder that "nothing to find" and "small" are independent properties. Case 020 deliberately varies the shape further: a multi-file diff entirely inside real `.c`/`.h` source files, including a comment edit three lines from previously-reviewed CVE logic (case 016) — testing whether a reviewer's silence tracks the diff's actual content rather than the file's own security-sensitive history. Keep testing all these shapes, and keep prioritizing more of this type relative to known-fix cases in the next batch.
- **Don't take a finding's own stated mechanism at face value just because the conclusion matches known ground truth** — but also don't assume a sophisticated-sounding mechanism is wrong just because your own first read of the code says so. Case 004: two findings reached a correct conclusion via a PoC that didn't actually reproduce. Case 013 is the mirror image: a finding's precise, non-obvious mechanism (an asymmetric condition between a reader "setup" and "reset" pair) looked wrong on a first, shallower trace of the code and turned out to be exactly right on a second, more careful one. Both outcomes required independent verification; neither was safe to infer from the conclusion alone.
- **A finding can be factually true and still be wrong for this review.** Case 008: a `Required` security finding reproduces exactly as claimed when executed, but the identical crash also reproduces against the base revision, making it pre-existing and out of scope per the disposition process's change-relevance check. Rejected on scope grounds despite being true.
- **A clean run is not automatically a correct run — check for the gap the reviewers *should* have raised, not just whether they raised anything.** Case 017: investigating past the one-line diff surfaced that the fix also silently dropped validation of where a symlink's target points, corroborated by the project's own master branch choosing a more aggressive fix to the same CVE class around the same time. All three reviewers returned zero findings on this case, missing that gap entirely — recorded honestly as a miss in the case's `outcomeNote`, not folded into "clean run, as expected" alongside genuinely clean cases like 016/018.
- **A known-fix case can still contain its own, unrelated bug.** Case 015: the live run did not come back clean the way its groundTruth anticipated — a confirmed `Required` finding caught a real, change-introduced Python-3 regression in the same commit that fixed the targeted CVE, verified by direct execution rather than assumed from the finding's text. The original groundTruth description was left as-is rather than retroactively rewritten; the discrepancy is recorded in the case's own notes, same practice as case 013.
- **Large real-world files need real budget headroom, and that's a policy-authoring fact, not a product defect.** Nine of the sixteen external cases (006, 010, 011, 012, 013, 014, 015, 018, 020) needed a raised `maxInputTokensPerReviewer`, a raised `--context-window`, or (013) a raised `timeoutSeconds` — notably, 015/018's ~101k-token baseline was hit by the fixed protocol-reserve overhead alone, not file size (both cases' actual changed content is under 25KB), while case 020 needed by far the largest budget yet (~420k tokens) purely because one of its five included files (`lib/http.c`) is 157KB even though only one of its lines changes. Expect some version of this for most real-repository cases going forward; it is not evidence of anything wrong with the reviewed change.
- **A CLI auto-update can silently outrun the adapter's version pin, and that's a correct refusal, not a bug.** Case 020 hit this directly: the host's Claude Code CLI auto-updated to 2.1.300 mid-task while `src/adapters/model/claude-code.js` still pinned 2.1.299, and preflight correctly refused (`CAPABILITY_UNAVAILABLE`) before any source preparation — the same situation, and the same fix (requalify at the user's explicit direction: bump the pin, update matching test/doc literals, rerun the deterministic suite and a live synthetic-suite check), as the corpus's first requalification from 2.1.296 to 2.1.299. Expect this to recur as the host CLI keeps updating; it is a control working as designed, not a corpus or product defect.
- `confirmedBlockingTruePositiveRate` is 7/8 (0.875) — `knownDefectCases`/`knownDefectMissedCount` is 4/0.
